# Xiaomi Ares MT6893 adaptation notes

Target branch: `7.3.3-mt6893-xiaomi-ares`

This is Ares-only work. Do not copy Chopin board definitions or set MT6891 identifiers.

## WL2866D regulator inventory

Reviewed references:
- Xiaomi vendor driver in `Tkpointz/android_kernel_aresin`, branch `lxr`.
- `arch/arm64/boot/dts/mediatek/ares-mt6893.dtsi` in the same reference tree.
- `wl2866d1.dtsi` is also present in that tree; its DVDD2 init-voltage differs from the board DTSI, so values must be reconciled against the actual Ares configuration before enabling rails.

| Output | Register offset | Range in reference DT | Step |
|---|---:|---:|---:|
| DVDD1 | 0 | 600000–1800000 µV | 6000 µV |
| DVDD2 | 1 | 600000–1800000 µV | 6000 µV |
| AVDD1 | 2 | 1200000–4300000 µV | 12500 µV |
| AVDD2 | 3 | 1200000–4300000 µV | 12500 µV |

**Reference init-voltage values are not fully consistent across fragments:**
- In `ares-mt6893.dtsi`: WL2866D1 DVDD1=1050000 µV, DVDD2=1260000 µV, AVDD1/2=2800000 µV. WL2866D2 DVDD1=1050000 µV, DVDD2=1200000 µV, AVDD1=2800000 µV, AVDD2=2700000 µV.
- In `wl2866d1.dtsi`: WL2866D1 DVDD2 is listed as 1200000 µV, not 1260000 µV.

The Ares board DTSI places WL2866D1 at I2C4 address 0x28 and WL2866D2 at I2C7 address 0x28. The Chopin DTS in this 7.3.3 branch instead has WL2866D1 on I2C7; that node must not be reused as an Ares wiring definition. Regulator output registers start at 0x03 plus channel offset; enable register is 0x0E and discharge register is 0x02.

## Porting requirements

- Use managed I2C/regmap and regulator registration APIs in this tree.
- Register one regulator per DT child; validate offset (0–3), exact channel-name/offset pairing, and voltage constraints.
- Enforce hardware voltage ceilings in the driver (DVDD 1.8 V, AVDD 4.3 V); reject out-of-range requests before writing the VSET register.
- Preserve enable bits for other outputs with `regmap_update_bits()`.
- Probe failures must propagate; do not return success on failed PID reads or failed regulator registration.
- Remove the legacy camera_ldo character device, unused ioctl, and debug sysfs controls from the initial port.
- Do not retain the vendor driver's panel-specific first-disable workaround; panel sequencing must be handled by the panel driver and tested separately.
- Review parent-supply voting before enabling it; reference regulator nodes do not currently define a parent supply.


## DT offset encoding correction

The Ares vendor DTS encodes each channel `offset` as a 16-bit property (`/bits/ 16 <...>`). The driver originally read this with `of_property_read_u32()`, which rejects a 2-byte property and would fail regulator child registration. The driver now tries 32-bit first, then 16-bit, and validates the resulting channel index 0–3. This fix is committed but not yet compile-tested.


## DTS integration state

The reference Ares DTS contains both WL2866D regulator nodes (I2C4/I2C7), but the 7.3.3 adaptation branch currently only has the Chopin DTS board file. The regulator driver alone is not sufficient to bring up the rails: a separate Ares board DTS and correct controller/pinctrl wiring are still required. Avoid copying the full Chopin DTS as an Ares board file.



## Controller integration evidence

The target SoC DTSI exposes controller labels `&i2c4` and `&i2c7` with controller IDs 4 and 7. Their addresses are 0x11D02000 and 0x11D03000, IRQs 0x74 and 0x77, respectively, and the base clock property is 400 kHz. The Ares vendor board reference places WL2866D1 at `&i2c4` address 0x28 and WL2866D2 at `&i2c7` address 0x28. The current Chopin board DTSI has camera clients on `&i2c4` and PMIC clients on `&i2c7`, but no matching Ares pin configuration is confirmed in the target tree; regulator-node integration is therefore held until board pinmux is validated.

## Regulator-core request-range handling

The legacy `.set_voltage` callback is used by this tree's regulator core directly (confirmed in `drivers/regulator/core.c`). A consumer may ask for a range whose lower bound is below the WL2866D's minimum, or whose upper bound is wider than the chip's maximum. The driver now clamps the lower bound to the hardware minimum, computes the first step at/above that voltage, and accepts the request if the resulting voltage fits the consumer's upper bound and the chip limit. It still rejects inverted ranges and requests with no realizable voltage. This logic is not compile- or hardware-tested yet.


## Datasheet cross-check (WL2866D Rev. 1.6)

Checked the vendor datasheet register map and voltage formulas against the initial driver. Register `0x00` is **Chip_REV** (read-only), not a product-ID field; the probe log was renamed accordingly. Voltage code zero is a valid output code (`0.6 V` for DVDD and `1.2 V` for AVDD), while the datasheet's default outputs (`1.2 V` and `2.8 V`) correspond to nonzero VSET codes `0x64` and `0x80`. The initial port's zero-code special case incorrectly returned the configured init-voltage for a live code-zero read; it has been removed so `get_voltage()` now uses the datasheet's linear formula for all codes. Regmap is also capped at the documented register range `0x00–0x0f`. These corrections are based on WL2866D Rev. 1.6: https://www.omnivision-group.com/wp-content/uploads/2022/09/WL2866D-V1.6.pdf

The driver descriptor now reports `n_voltages = 0`, because it exposes continuous `.set_voltage` control and has no discrete `list_voltage()` selector table. The regulator core in this target tree takes the direct callback path; the zero count avoids advertising a fake single-selector voltage.



## Discharge register update

Datasheet Rev. 1.6 defines register `0x02`: bits 0–3 individually enable discharge for DVDD1, DVDD2, AVDD1, AVDD2, and bit 7 must be set when discharge is used. The driver now sets mask/value `0x8f` using `regmap_update_bits()` so the four channels and master bit are enabled while bits 4–6 (not described as discharge controls) are preserved instead of overwritten. The vendor driver writes `0xff`; this port deliberately narrows the write to documented control bits. This has not been validated on the board yet.


## Build-system cleanup

The port previously had duplicate `REGULATOR_WL2866D` Kconfig declarations and duplicate `wl2866d.o` Makefile entries (one old description incorrectly claimed Chopin i2c7/i2c9 and panel DVDD routing). The duplicate entries have been removed, leaving one Ares-focused symbol with `depends on I2C && OF` and `select REGMAP_I2C`. This is verified by reading the branch's current Kconfig/Makefile after the cleanup; compilation remains unverified.

## Validation still required

The initial driver port is not compiled or device-tested yet. Compile against the branch's regulator API, then validate on-device rail readback, consumer mappings, display/camera power sequencing, and boot/recovery before treating it as usable.
